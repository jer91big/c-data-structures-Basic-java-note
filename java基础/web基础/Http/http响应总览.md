上一次我们聊了 HTTP 请求的“长相”**（由请求行、头、空行、体组成）。这次我们换个角度，从**全生命周期（幕后发生了什么）**以及**核心对比（比如大家常问的 GET 与 POST 的深层区别）来进一步深入。

  

## 一、 一个 HTTP 请求的完整生命周期（幕后发生了什么？）

当你真正在浏览器输入网址或点击按钮时，发送一个 HTTP 请求其实触发了一系列复杂的底层操作：

  

1. **DNS 解析（域名转换）**
    
      
    - 浏览器拿到网址（如 `api.example.com`），先去查本地缓存或向 DNS 服务器发送请求，把人类可读的**域名翻译成机器能识别的 IP 地址**。
        
          
        
2. **建立 TCP 连接（三次握手）**
    
      
    - 客户端找到目标服务器的 IP 和端口（默认 HTTP 是 80，HTTPS 是 443）后，通过三次握手建立可靠的传输层 TCP 连接。
        
          
        
    - **如果是 HTTPS**：在此之后还要进行 **TLS/SSL 握手**，交换密钥，协商加密算法，确保后续传输的数据被加密。
        
          
        
3. **发送 HTTP 请求（报文传输）**
    
      
    - 客户端按照我们上回讲的格式（请求行、请求头、空行、请求体），把数据通过已建立的 TCP 通道发送给服务器。
        
          
        
4. **服务器处理与响应**
    
      
    - 服务器接收到报文，解析请求，执行业务逻辑（如查数据库、调用微服务），然后把处理结果包装成 **HTTP 响应**（状态码、响应头、响应体）返回给客户端。
        
          
        
5. **断开或复用连接（Keep-Alive）**
    
      
    - 现代 HTTP/1.1 和 HTTP/2 默认支持长连接（`Connection: keep-alive`），这意味着 TCP 连接不会立刻断开，浏览器可以在同一个连接上继续发送下一个请求，省去了频繁建链的开销。
        
          
        

## 二、 面试/开发常考：GET 与 POST 的深层区别

虽然 GET 和 POST 都是 HTTP 请求方法，但它们在设计哲学和实际使用中有很大的不同：

  

|**维度**|**GET 请求**|**POST 请求**|
|---|---|---|
|**主要目的**|**获取（读取）**服务器上的资源|**提交（创建/修改）**服务器上的数据|
|**数据传递位置**|参数拼接在 **URL 的查询字符串（Query String）** 中（如 `/search?q=apple`）|参数放在 **请求体（Request Body）** 中|
|**安全性**|**安全**（只读不改，不应引起服务器状态改变）|**不安全**（会修改服务器端的数据状态）|
|**幂等性**|**幂等**（无论请求多少次，服务器资源都不会变）|**非幂等**（每发一次 POST，服务器可能就多创建一条记录）|
|**数据长度限制**|受限于浏览器和服务器对 **URL 长度的最大限制**（通常几 KB 到几十 KB 左右）|理论上**没有限制**（取决于服务器配置的 Body 最大允许大小）|
|**数据可见性**|参数明文显示在 URL 栏中，容易被记录在浏览器历史记录或日志中|参数在请求体中，相对不那么直观（但如果没加密，抓包依然能看到）|
|**缓存机制**|**可以**被浏览器主动缓存（除非特别声明不缓存）|**默认不缓存**|

### 💡 核心误区纠正

很多人误以为：**“GET 不能传很长的参数，POST 比 GET 更安全”**。

  

- 实际上，HTTP 协议本身**没有**规定 GET 的 URL 长度限制，限制是由浏览器和 Web 服务器（如 Nginx、Tomcat）出于安全和性能考虑设定的。
    
      
    
- 关于安全性，POST 的请求体和 GET 的 URL 一样，如果不走 HTTPS，在网络上传输时都是**明文**的，都可以被抓包工具（如 Wireshark、Charles）轻易截获。因此，真正的安全必须依赖 **HTTPS（加密传输）**。
